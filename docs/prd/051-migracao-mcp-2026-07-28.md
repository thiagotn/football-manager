## 1. Contexto e motivação

Em 28/07/2026 foi publicada a revisão **2026-07-28** da spec do Model Context Protocol, e a
Anthropic anunciou que o suporte está sendo ativado gradualmente nos produtos Claude
([post oficial](https://claude.com/blog/bringing-mcp-2026-07-28-to-claude)). As mudanças
relevantes ([changelog completo](https://modelcontextprotocol.io/specification/2026-07-28/changelog)):

- **Core stateless**: fim do handshake `initialize`/`notifications/initialized` e do header
  `Mcp-Session-Id`. Cada request carrega versão de protocolo e capabilities em `_meta`
  (`io.modelcontextprotocol/protocolVersion` etc.). Servidores podem rodar atrás de
  load balancer round-robin sem sticky sessions.
- **`server/discover`**: novo RPC obrigatório — o servidor anuncia versões suportadas,
  capabilities e identidade.
- **`resultType` obrigatório** em todo resultado (`"complete"` ou `"input_required"` para o
  novo padrão MRTR, que substitui requests iniciados pelo servidor).
- **Cache hints**: `ttlMs` e `cacheScope` obrigatórios nos resultados de `tools/list` e afins;
  ordem determinística de tools recomendada (melhora prompt cache dos clientes).
- **Headers obrigatórios** no Streamable HTTP: `Mcp-Method` e `Mcp-Name` em todo POST.
- **Deprecações**: Roots, Sampling e Logging (janela mínima de 12 meses); transporte HTTP+SSE
  reclassificado como Deprecated; `resources/subscribe` substituído por `subscriptions/listen`.

O **SDK Python oficial** acompanha via **`mcp` v2** (beta `2.0.0b1`, [anúncio](https://blog.modelcontextprotocol.io/posts/sdk-betas-2026-07-28/)),
com [guia de migração v1→v2](https://py.sdk.modelcontextprotocol.io/) próprio. Ponto-chave de
compatibilidade: **um servidor v2 responde tanto `server/discover` quanto o `initialize` legado**,
então clientes atuais (Claude CLI, Copilot, chat rachao.app) continuam conectando durante a
transição.

**Por que agora**: o `football-mcp` tem pin aberto `mcp[cli]>=1.0` e **não tem lockfile** — quando
a v2 estável for publicada, qualquer rebuild da imagem Docker resolveria o SDK novo e **quebraria
o servidor em produção sem nenhuma mudança de código nossa** (`ModuleNotFoundError:
mcp.server.fastmcp`). Migrar proativamente com pin exato elimina esse risco e já nos coloca na
spec nova.

> **Nota sobre FastMCP (gofastmcp.com)**: avaliado e descartado. O FastMCP v2/v3 standalone
> **não** suporta a spec 2026-07-28 (só o FastMCP 4.0.0b1 suportaria), e trocar de framework
> seria uma migração maior sem benefício para a superfície atual (15 tools, sem
> resources/prompts). O caminho natural é continuar no SDK oficial.

## 2. Estado atual do football-mcp

| Item | Estado |
|---|---|
| SDK | `mcp[cli]>=1.0` (venv local: 1.27.0), classe `FastMCP` de `mcp.server.fastmcp` |
| Lockfile | Inexistente — Docker resolve deps no build (`uv pip install` a partir do pyproject) |
| Servidor | `rachao_mcp/server.py` — `FastMCP("rachao.app", transport_security=...)`; tools registradas programaticamente via `server.tool()(fn)` sobre `READ_TOOLS`/`WRITE_TOOLS` |
| Transportes | Env `MCP_TRANSPORT`: `stdio` (default, uso local via Claude CLI), `http` (streamable-http — **produção**), `sse` (legado, sem uso conhecido) |
| Auth | `BearerTokenMiddleware` (ASGI) → ContextVar por request; fallback env `RACHAO_TOKEN` (`auth.py`, `middleware.py`) — **independente do SDK** |
| Tools | 15 (10 read / 5 write); sem resources, prompts, sampling, elicitation ou logging MCP |
| Testes | `tests/` (pytest + respx); `test_guardrails.py` acessa interno `server._tool_manager._tools` |
| Deploy | `football-api/docker-compose.prod.yml`, serviço `mcp` (`MCP_TRANSPORT: http`, `0.0.0.0:8080`, Traefik em `mcp.rachao.app`); imagem `ghcr.io/thiagotn/football-manager-mcp` |
| Protocolo | Nenhuma versão hardcoded — negociação 100% delegada ao SDK |

A superfície é mínima (só tools, tudo async, auth fora do SDK), o que torna a migração pequena
e mecânica.

## 3. Mapa de impacto — mudança do SDK v2 → código do football-mcp

Verificado contra o wheel real de `mcp==2.0.0b1` (2026-07-31):

| Mudança no SDK v2 | Impacto | Arquivo |
|---|---|---|
| Pin exato obrigatório (`pip` sem pin fica na 1.x) | `mcp[cli]>=1.0` → `mcp[cli]==2.0.0b1` | `pyproject.toml` |
| `FastMCP` → `MCPServer` (`mcp.server.fastmcp` **não existe** no b1) | Trocar import e construtor: `from mcp.server.mcpserver import MCPServer`; `MCPServer("rachao.app", version="0.1.0")` (sem `version`, v2 reporta string vazia) | `rachao_mcp/server.py` |
| `transport_security` sai do construtor → vai para `run()` / `sse_app()` / `streamable_http_app()` (confirmado na assinatura do b1) | Mover o kwarg para `streamable_http_app(transport_security=...)` (e `sse_app(...)` se o modo for mantido) | `rachao_mcp/server.py` |
| Demais params de transporte também migram para `run()`/app methods | Avaliar `streamable_http_app(stateless_http=True, json_response=True)` — recomendado: é o modo alinhado ao core stateless da spec e o servidor não usa nenhum recurso com back-channel | `rachao_mcp/server.py` |
| Lifespan do Streamable HTTP entra uma vez no startup do session manager | Hoje o app roda via `uvicorn.run(BearerTokenMiddleware(raw_app))` — validar que o middleware repassa o scope `lifespan` intacto (senão: `RuntimeError: Task group is not initialized`) | `rachao_mcp/middleware.py` (verificação) |
| Decorators `@tool()` inalterados | `server.tool()(fn)` continua funcionando sem mudança | `rachao_mcp/tools/*` |
| Testes não devem depender de internos | `_registered_tool_names()` troca `server._tool_manager._tools` pela API pública `await server.list_tools()` (existe no b1) | `tests/test_guardrails.py` |
| `McpError`→`MCPError`, snake_case em types, `mcp.types` → pacote `mcp-types` | **N/A** — o pacote não importa `mcp.types` nem `McpError` | — |
| Handlers sync rodam em worker thread | **N/A** — todas as tools são async | — |
| Roots / Sampling / Logging deprecados (SEP-2577) | **N/A** — não usados | — |
| HTTP+SSE reclassificado Deprecated | Remover o modo `MCP_TRANSPORT=sse` (sem uso em prod) ou documentá-lo como deprecated no Makefile/README | `rachao_mcp/server.py` |
| Dependências | b1 exige Python ≥3.10 (imagem `python:3.11-slim` OK) e **ainda usa `httpx`/`httpx-sse`** — a troca por `httpx2` descrita no guia de migração só chega em beta posterior/estável. Nosso `httpx`+`respx` (`client.py`, testes) seguem intocados | `Dockerfile`, `pyproject.toml` |
| Compose / infra | Nenhuma mudança: envs, porta 8080 e Traefik permanecem | `docker-compose.prod.yml` |

**Melhoria oportunista (mesmo PR)**: o dict `annotations` de cada tupla em
`READ_TOOLS`/`WRITE_TOOLS` (readOnlyHint/destructiveHint/idempotentHint) é hoje carregado e
**ignorado**. Passar `server.tool(annotations=...)` no `register()` expõe os hints no protocolo —
clientes (Claude) usam isso para pedir menos confirmações em tools read-only.

## 4. Passos de execução

Ordem sugerida pelo guia oficial de migração:

1. **Pin**: `mcp[cli]==2.0.0b1` no `pyproject.toml`; `make install`; conferir resolução
   (traz `mcp-types==2.0.0b1`, `opentelemetry-api`, `sse-starlette>=3`).
2. **Renames mecânicos** em `server.py`: import `mcp.server.mcpserver`, `FastMCP`→`MCPServer`,
   adicionar `version="0.1.0"`.
3. **Transporte**: mover `transport_security` para `streamable_http_app()`/`sse_app()`;
   habilitar `stateless_http=True` + `json_response=True` no modo `http`; decidir remoção do
   modo `sse`.
4. **Testes**: trocar `_tool_manager._tools` por `await server.list_tools()`;
   rodar `cd football-mcp && python3 -m pytest tests/ -q` (obrigatório antes de commit no MCP;
   atenção ao set hardcoded de 15 tools em `test_guardrails.py`).
5. **Smoke stdio**: `make dev` + Claude CLI local (`make register`).
6. **Smoke http local**: `MCP_TRANSPORT=http` + `curl` — POST com headers `Mcp-Method`/`Mcp-Name`;
   validar `server/discover` **e** o fallback `initialize` (cliente legado).
7. **Deploy**: rebuild da imagem, `docker compose -f docker-compose.prod.yml up -d mcp` no VPS;
   validar `mcp.rachao.app` com token pessoal (PRD 040) e o chat do rachao.app (PRD 042).
8. **Opcional no mesmo PR**: propagar `annotations` das tools (melhoria acima).

### Notas da execução (2026-07-31)

- **`uv` exige `--prerelease=allow`**: o pin exato `mcp==2.0.0b1` puxa `mcp-types==2.0.0b1`
  como dependência *transitiva* pré-release, que o `uv` recusa sem a flag. Ajustado no
  `Dockerfile` e necessário no `make install` local (`VIRTUAL_ENV=.venv uv pip install
  --prerelease=allow -e ".[dev]"`).
- **Roteamento de era no b1 é pelo header `MCP-Protocol-Version`**: um POST com
  `MCP-Protocol-Version: 2026-07-28` vai para o handler moderno (stateless); sem o header,
  cai no caminho legado (onde `server/discover` retorna -32601). Requests modernos também
  exigem o envelope em `params._meta` (`io.modelcontextprotocol/protocolVersion`,
  `clientInfo`, `clientCapabilities`).
- **SSE removido** (opção da tabela §3): `MCP_TRANSPORT=sse` agora falha com mensagem clara
  apontando para `http`.
- **Annotations propagadas**: os dicts camelCase das tools constroem `ToolAnnotations`
  diretamente (aliases aceitos) — `tools/list` agora expõe `readOnlyHint`/`idempotentHint`.
- Smokes validados: `initialize` legado (`serverInfo 0.1.0`), `server/discover`
  (`supportedVersions: ["2026-07-28"]`), `tools/list` stateless (com `resultType`,
  `cacheScope`) e `tools/call` com Bearer por request atravessando o
  `BearerTokenMiddleware` (lifespan do session manager OK atrás do middleware).
- **Deploy real é no homelab, não no VPS** (§2 estava desatualizado): o MCP roda no k3s
  (`rachao-mcp` no namespace `rachao`, manifests em `homelab/helm/apps/rachao/`), atrás de
  `mcp.rachao.app`, apontando para a API Go v2 interna. Fluxo: `main.yml`
  (workflow_dispatch) publica `ghcr.io/thiagotn/football-manager-mcp:<sha>` → bump do
  `newTag` em `homelab/helm/apps/rachao/kustomization.yaml` → Argo CD faz o rollout.
  Deploy de 2026-07-31 (tag `91f2a4f7`): rollout OK, smokes das duas eras validados em
  produção via `https://mcp.rachao.app/mcp`.
- O CI (`main.yml`, job `mcp-tests`) também precisou de `--prerelease=allow` no
  `uv pip install`.

## 5. Compatibilidade, riscos e rollback

- **Clientes atuais continuam funcionando**: o servidor v2 responde o `initialize` legado além
  de `server/discover` — Claude CLI/Copilot/chat não precisam mudar nada.
- **Risco de beta**: a API pode ajustar até a estável (ex.: swap `httpx`→`httpx2` já anunciado
  no guia). Mitigação: pin exato `==2.0.0b1`; ao sair a estável, bump deliberado para
  `mcp[cli]>=2,<3` revisitando o guia (seção `httpx2` em particular).
- **Ponto de atenção**: lifespan do session manager atrás do `BearerTokenMiddleware`
  (item da tabela §3) — testar o modo http logo no passo 6, não só no deploy.
- **Rollback**: reverter o pin para `mcp[cli]>=1.0,<2` + rebuild. Nenhuma mudança de env,
  porta ou infra é necessária em nenhuma direção.

## 6. Fora de escopo / follow-ups

- **FastMCP 4.0 (gofastmcp)** — descartado nesta decisão.
- **Extensão de tasks** (`io.modelcontextprotocol/tasks`) e **MCP Apps** — sem caso de uso atual.
- **OAuth completo no servidor MCP** — mantém-se o modelo Bearer com tokens pessoais
  (PRD 040/041); o hardening OAuth da spec afeta servidores que atuam como resource server
  OAuth, o que não é o caso.
- **Lockfile (`uv.lock`) para o football-mcp** — recomendado como follow-up independente para
  builds reproduzíveis.
